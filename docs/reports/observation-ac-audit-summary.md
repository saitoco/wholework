# observation AC 実査 集約レポート (#1270)

再型付けされた `verify-type: observation` の post-merge AC を「発火時に判定可能か」で実査し、判定不能分を retire (分類 D) ・`manual` へ差し戻し (分類 E) する取り組みの集約レポート。AC 行単位の実査は 3 本の sub-issue (#1274 / #1275 / #1276) が担い、本レポートはその baseline と集約結果を記録する。

## Baseline (実装前スナップショット)

**計測日時**: 2026-08-08 (UTC)
**計測時点**: sub-issue #1274 / #1275 / #1276 の着手前 (retire・差し戻しによる母集団変化の発生前)

親 #1270 Notes「実行順序の制約」により、baseline は 3 sub-issue の着手前に確定させる必要がある。retire が始まると母集団が変化し、この数値は再取得不能になる。

### 計測方法 (post-merge で同一手順を再現すること)

```bash
# 1. 候補母集団の凍結 (副作用なし)
scripts/observation-trigger.sh --event auto-run --dry-run

# 2. 各候補 Issue の AC 行を計数
#    対象行の条件: 行頭 "- [ ]" かつ verify-type: observation かつ event=auto-run
```

`--dry-run` を用いるのは、通常実行が全マッチ Issue に通知コメントを投稿する副作用を持つため。

### verify-type 抽出方式の一致確認

#1273 が扱うタグ抽出の誤分類が本計測に影響しないことを確認した。substring 方式 (現行 `opportunistic-search.sh` と同等) と HTML コメント限定方式の双方で計数し、**両者は 85 行で完全一致 (不一致 0 行)** した。

### baseline の単位 — 「率」ではなく「母集団」とする決定 (2026-08-09)

**baseline の単位は候補母集団の実数 (82 Issue / 85 AC 行) である。SKIPPED 率は採らない。**

#### 率を採れない理由

当初の親 Pre-merge AC 1 は分母を「1 回の dispatch で候補に挙がった observation AC 行数」、分子を「そのうち SKIPPED を返した行数」と定義していたが、**この 2 つは 1 回の dispatch では両立しない**。

`skills/auto/SKILL.md` Step 5 の dispatch は `observation-dispatch-threshold` (既定 5) 件を上限とするため、1 回の実行で実際に `/verify` へ渡り SKIPPED/PASS が確定するのは最大 5 行である。分母 85 に対する分子は構造上 5 が上限となり、率としての意味をなさない。

| 読み | 分母 | 分子 | 評価 |
|---|---|---|---|
| 読み 1 | 85 (候補全体) | 実 dispatch 分の SKIPPED | 率が上限 5/85 に張り付き無意味 |
| 読み 2 | 実 dispatch 数 (5) | そのうちの SKIPPED | dispatch 効率としては有意だが n=5 で分散が大きい |

読み 2 は指標としては意味を持つが、単発測定の分散が大きく baseline に適さない。`/verify 1270` は当初定義の AC 1 を **UNCERTAIN** と判定した (実装側に不足はなく、AC の定義自体が充足不能だったため)。

#### 採用した単位

**候補母集団の実数**とし、Pre-merge AC 1 / Post-merge AC 8 の双方をこの単位へ揃えた。

| 項目 | baseline (2026-08-08) |
|---|---|
| 候補 Issue 数 | **82** |
| 候補 observation AC 行数 | **85** |

post-merge では上記「計測方法」節と同一手順で再計測し、baseline からの減少を確認する。D の retire (5 行) と E の `manual` 差し戻し (15 行) により**約 20 行の減少**を見込む。

率を諦める代わりに、baseline / post-merge の双方が同一手順で機械的に再現でき、単発測定の分散に影響されない指標になる。AC 1 だけでなく Post-merge AC 8 も同じ単位へ揃えたのは、片方だけ直すと比較の単位が食い違うためである。

#### 参考値 (baseline ではない)

直近の実 dispatch 事例が 1 件ある。セッション `94570-1786069858` (2026-08-07) で昇順先頭 5 件 (#446 / #477 / #478 / #484 / #486) を評価した際、判定可能と見込まれたのは #484 のみで残り 4 件は前提不成立により SKIPPED 見込みだった (**4/5 = 80%**)。ただしこれは実 dispatch ではなく事前評価であり、かつ当該セッションは最終的に選抜方法を変更している (`docs/sessions/94570-1786069858-2026-08-07/session.md` § Observation Dispatch 結果) ため、参考値として扱う。

### D と E の内訳 (型間移動の可視化)

observation waiting は **20 行減少**するが、その内訳は次のとおりで、**純減は 5 行のみ**である。

| 経路 | 行数 | observation waiting への影響 | manual waiting への影響 |
|---|---|---|---|
| **D (retire)** | **5** | −5 (純減) | 変化なし |
| **E (`manual` へ差し戻し)** | **15** | −15 | **+15** |
| 小計 | 20 | **−20** | **+15** |

**この区別が本レポートの要点である。** observation waiting の 20 行減少を「20 行分の改善」と読むのは誤りで、実際に条件そのものが消えたのは 5 行 (25%) にすぎない。残る 15 行 (75%) は判定経路が `manual` へ移っただけであり、条件は生きている。

なお A 29 行 / B 8 行 (合計 37 行、65%) は observation のまま維持される。B は条件文の書き換えのみで型は変わらない。

この結果は #1158 の前提に対する反証でもある。#1158 は「manual には発火契機がない」として 57 行を observation へ移したが、本実査では **15 行が `manual` へ戻された**。実測上 `manual` の消化率 74% は `observation` の 48% を上回っており (`scripts/collect-verify-retention-stats.sh --window 2026-05-07`、2026-08-08)、移動の方向自体が逆だった行が一定数あったことになる。

### E の内訳 (capability 待ちの分離)

| 区分 | 行数 | 内訳 |
|---|---|---|
| 今すぐ `/verify` で判定できる | **15** | #1274: 2 / #1275: 7 / #1276: 6 |
| 装備待ち (`capability=<key>` 併記) | **0** | 該当なし |

**装備待ちは 0 行だった。** 3 本の sub-issue がいずれも独立に「`.wholework.yml` の capability 不足が理由の差し戻しは無い」と結論している。

E 15 行の差し戻し理由は次の 3 型に収まる。いずれも装備の問題ではなく **観測窓の性質**の問題である。

1. **event の発火が観測対象を生成しない** — `auto-run` の発火は `/auto` が完走したことしか保証せず、条件文が要求する内容的性質を持つ成果物や特定環境での実行は保証しない。`/verify` 実行時に Claude が能動的にシナリオを構築するか蓄積済み成果物を横断検索すれば判定できる
2. **統計的・定性的トレンド判断** — 単発の event 発火では信号を持たない
3. **特定内容の Issue/PR が発生しない限り観測窓が開かない** — 受動的な待機では観測できない

#1278 の `capability-unavailable` 区分へ引き継ぐ行は本 Issue からは発生しない。装備待ちのケースは observation ではなく `manual` バケツ側に存在すると見られる (#1167 が D1 と判定した #1059 / #709 / #548 / #442 / #441 など) ため、#1278 の実測がその母集団を扱う。
