# Opus 5 Effort Recalibration: `run-spec.sh --opus`

**Report date**: 2026-08-07
**Issue**: #1064 (`docs/reports/claude-opus-5-impact-strategy.md` §4.4/§8, the symmetric counterpart to #922/C3)
**Scope**: Re-evaluate whether `run-spec.sh`'s Opus fallback path (`--opus`, L-size Issues only) default effort (`xhigh`, set in #217 under Opus 4.8's guidance) is still appropriate under Opus 5's effort-calibration guidance, and whether the `--max` explicit-override flag's positioning still holds.
**Depends on**: `docs/reports/claude-opus-5-impact-strategy.md` §3.2/§4.4 (candidate framing); Issue #217 (2026-04-17, introduced Opus path `max`→`xhigh`, Sonnet path explicitly out of scope); Issue #922 (`docs/reports/sonnet-5-effort-recalibration-spec.md`, C3, Sonnet-path evaluation that explicitly scoped the Opus fallback out — this report evaluates that scoped-out side); Issue #1228 (spec/issue phase telemetry gap fix — prerequisite for future empirical validation, not yet reflected in production samples as of this report).

## Background

`run-spec.sh --opus` sets `MODEL="opus"` / `EFFORT="xhigh"` (`scripts/run-spec.sh:15-18`). `--opus` is invoked by exactly one caller — `scripts/run-auto-sub.sh:845`, `if [[ "$SIZE" == "L" ]]` — so this path is scoped to Size L Issues only (XL Issues are split into sub-issues before `/spec` runs, so they never reach this branch). The `xhigh` default was set in #217 under Opus 4.8's own calibration guidance ("`xhigh` is the Opus 4.8 recommended default for most coding and agentic use cases," `docs/tech.md`'s "Opus 4.8 effort calibration" note).

Since 2026-07-24, the `opus` CLI alias auto-resolves to Opus 5 rather than Opus 4.8 (per the alias pin policy), so this path has been running on Opus 5 for approximately two weeks as of this report, on the same `xhigh` setting chosen under Opus 4.8's guidance. `docs/reports/claude-opus-5-impact-strategy.md` §3.2 documents that Opus 5's own calibration guidance changed materially from Opus 4.8's: coding/agentic tasks should still *start* at `xhigh`, but the guidance now explicitly recommends sweeping *downward* from that starting point, because `low`/`medium` are reported to perform more strongly than their tier names suggest — the opposite emphasis from Opus 4.8's guidance, which recommended `xhigh` as close to an upper-bound default and flagged `max` as an overthinking risk. §4.4 of that report frames this Issue precisely: "the existing `xhigh` default... may still be correct, but the rationale it was chosen for no longer matches Opus 5's actual guidance and needs its own re-evaluation pass rather than being carried forward unexamined."

`#922` (C3) evaluated the sibling question for `run-spec.sh`'s **Sonnet** default path (all Issue sizes) and concluded **maintain `max`**, explicitly declining to treat the Opus fallback's `xhigh` as transferable evidence in either direction: "The Opus fallback's `xhigh` default is not treated as transferable evidence, since it reflects Opus 4.8's own (distinct) effort-calibration guidance for a narrower, L-size-only scope." This Issue is the direct counterpart that formally evaluates that previously-scoped-out side, now under Opus 5's guidance rather than Opus 4.8's.

As with #922, no quantitative A/B benchmarking harness exists for isolating effort-level impact on spec quality for a single task — re-running the same Issue's `/spec` at multiple effort levels is not practical in production, and doing so non-interactively would spend real Issues' state and Opus 5's premium per-token cost without a controlled comparison. This report follows the same combined-evidence method #922 established: (a) qualitative structural analysis of the `/spec` workload (unchanged by which model runs it), (b) whether the guidance shift documented in `docs/tech.md` actually applies to this specific path, and (c) a check of whatever production signal exists — in this case, telemetry and a wall-clock proxy, both addressed in Analysis 4 below.

## Evaluation Method

1. **Re-confirm the current implementation and dispatch scope.** Verify `scripts/run-spec.sh:15-18` (`--opus` → `MODEL="opus"`/`EFFORT="xhigh"`) and `scripts/run-auto-sub.sh:845` (`--opus` passed only when `SIZE == "L"`) match the Issue's framing, and confirm no other caller invokes `--opus`.
2. **Structural analysis of `/spec`, re-applied to the Opus path.** `#922`'s Analysis 2 established that `/spec` is a single, unbroken 19-step reasoning chain with no sub-agent fan-out, and that a shallow-reasoning error ships as Implementation Steps that `/code` executes largely at face value — propagating through code, review, and merge (three downstream phases) before it can be caught. This structural fact is a property of `skills/spec/SKILL.md` itself, independent of which model executes it, so it applies identically to the `--opus` path.
3. **Determine whether the Opus 4.8→5 guidance shift (§3.2) directly applies here, unlike #922's Opus-4.8-note-doesn't-transfer-to-Sonnet finding.** Opus 5's calibration guidance is about Opus 5's own effort ladder, and the `--opus` path actually runs on Opus 5 — so, unlike #922 (where the diminishing-returns claim was scoped to Opus 4.8 and did not generalize to Sonnet 5), the mismatch #922 relied on to block the Sonnet path's downgrade does not exist here. This asymmetry must be addressed directly rather than mechanically re-applying #922's "doesn't transfer" conclusion.
4. **Telemetry and production-sample check.** Confirm the current state of `--opus` token-usage telemetry (per #1228) and whatever wall-clock proxy data exists, per the Issue Notes' pre-identified sources.
5. **`--max` flag positioning check.** Assess whether the `--max` explicit-override semantics (force `EFFORT="max"` regardless of `--opus`/`--fable`) still match Opus 5's guidance for when `max` is appropriate.

## Analysis 1 — Implementation and dispatch scope re-confirmation

`scripts/run-spec.sh:15-18`:
```
--opus)
  MODEL="opus"
  EFFORT="xhigh"
```
`scripts/run-auto-sub.sh:845`: `if [[ "$SIZE" == "L" ]]; then "$SCRIPT_DIR/run-spec.sh" "$SUB_NUMBER" --opus; else ...`. This is the only call site in the repository that passes `--opus`. Both match the Issue's Background exactly — no drift found. `docs/tech.md`'s matrix row ("Opus: xhigh (default), max (explicit `--max`)") also matches. This confirms the evaluation is starting from an accurately-documented baseline, same as #922's Analysis 1 finding for the Sonnet path.

## Analysis 2 — Structural risk profile (unchanged by the Opus 4.8→5 model swap)

`#922`'s structural argument for the Sonnet path applies identically here, because it is a property of the skill, not the model: `skills/spec/SKILL.md` runs as a single agent with no sub-agent fan-out (the L/XL parallel investigation sub-agents `issue-scope`/`issue-risk`/`issue-precedent` belong to `/issue` Step 12a, not `/spec`), executing a single continuous multi-step reasoning chain (mode detection → Issue fetch → worktree entry → codebase investigation → ambiguity resolution → Spec creation → retrospective). There is no independent sub-agent positioned to re-check a shallow-reasoning error introduced early in the chain — an error made at low effort is not caught by a second pass at a different effort tier the way a review sub-agent might catch a code-phase mistake. Once such an error ships as an Implementation Step, `/code` executes it largely at face value, and the error propagates through code, review, and merge — three downstream phases — before it can surface, exactly as #922 and the impact report's §4.4 both describe.

This risk profile is, if anything, *narrower but sharper* for the `--opus` path specifically: `--opus` is invoked only for Size L Issues (Analysis 1), which are by construction the most complex Issues in the pipeline — Opus is deliberately routed to this subset precisely because the reasoning demands exceed what the Sonnet default path is trusted with. A general cross-workload recommendation to "sweep downward because low/medium are stronger than expected" is calibrated against Opus 5's typical task mix; it is not a claim that L-size specs specifically — the highest-complexity, highest-blast-radius subset — have headroom to spare. Applying a general downward-sweep recommendation uniformly to a deliberately-carved-out hardest-case subset repeats the same size-scoping mismatch #921 (C2) found when the Sonnet-5 impact report's `medium` candidacy for `run-code.sh` (scoped to XS/S patch-route) was read as applying to the global `--effort` flag.

## Analysis 3 — Does the Opus 5 downward-sweep guidance directly apply, and does that settle the question?

Unlike #922, where the only diminishing-returns claim on record ("Opus 4.8 effort calibration" note) was explicitly scoped to Opus 4.8 and did not transfer to Sonnet 5's own effort curve, the guidance at issue here — §3.2's Opus 5 calibration guidance — is about the exact model this path runs on. There is no model-generation mismatch to dismiss the guidance on. This is a real asymmetry from #922's case and must be weighed honestly rather than waved away by analogy.

However, direct applicability of the *guidance* is not the same as sufficiency of *evidence* to act on it for this specific path. The guidance itself is a recommendation to **sweep and check**, not a claim that a specific lower tier (e.g. `high` or `medium`) is already known to match `xhigh`'s quality for this workload — Anthropic's own framing is exploratory ("low/medium are reported to be stronger than their tier names suggest... sweep downward"), not prescriptive of a specific target tier. Acting on it responsibly requires either (a) a controlled comparison showing a lower tier holds up for this specific workload, or (b) a sufficiently strong structural/production signal that the current tier is over-provisioned. Section Analysis 4 below establishes that neither exists yet for `--opus` specifically. In the absence of either, "the guidance recommends checking" is not equivalent to "checking is safe to skip and the answer is presumed to be yes" — particularly for the single highest-blast-radius, highest-complexity-by-construction workload in the entire effort matrix (Analysis 2).

This reasoning differs from #922's in mechanism (there: guidance doesn't transfer; here: guidance transfers but there is no safe way to act on it yet without evidence) but arrives at a structurally similar posture: **the conservative default (maintain) is correct in the absence of evidence, not because the guidance is irrelevant, but because acting on directional guidance without any way to validate the outcome — for the pipeline's most consequential and highest-complexity phase — is not a responsible substitute for that evidence.**

## Analysis 4 — Telemetry and production-sample check

**Telemetry state**: Issue comments (2026-08-06, 2026-08-07) identified that the spec phase never emitted `token_usage`/`wrapper_exit` events, blocking any telemetry-based evaluation of `--opus` specifically. This was resolved by `#1228` (commit `edd4cc10`, merged the same day as this Issue's `/spec` execution) — `run-spec.sh` now emits both events via the `_EMIT_PHASE_OWNED` gate. However, because the fix landed only just before this report, `.tmp/auto-events.jsonl` contains **zero** `token_usage` records for `--opus` runs as of this report (re-confirmed directly: `grep -c opus .tmp/auto-events.jsonl` → 0; no opus-tagged `token_usage` events found). The instrumentation gap is closed, but no real sample has yet accumulated behind it.

**Sampling pitfall (recorded per Issue Notes)**: "Size L Issue" is not equivalent to "Opus-generated Spec." Size promotion (M→L) inside `/spec`'s own execution happens *after* the Opus/Sonnet dispatch decision in `run-auto-sub.sh` (which reads the Issue's Size at spec-dispatch time), so a Spec that ends up Size L by the time it is filed may have been generated by Sonnet, not Opus (confirmed example: #1175 — triaged at Size M, spec began on Sonnet, then promoted to Size L mid-spec after 7 Changed Files were identified). Any future sample-based evaluation must extract the Opus-generated subset specifically via the `sub_start` event's `size=L` field (captured at dispatch time, before any mid-spec promotion) or the wrapper log's `Model:` line — not by filtering the resulting Spec's final recorded Size.

**Wall-clock proxy (secondary, confounded)**: filtering `sub_start` events by `size=L` (the correct dispatch-time signal per the pitfall above) gives 9 Opus-5-generation spec runs (2026-07-24 onward) averaging 16 minutes 22 seconds, versus 5 Opus-4.8-generation runs averaging 13 minutes 22 seconds — a +22% increase, at the *same* `xhigh` effort in both periods (this report does not compare effort levels; it compares model generations at a fixed effort). Both periods overlap with documented high-concurrent-session-load windows (`docs/reports/external-kill-investigation.md`), so this cannot be treated as a clean model-generation effect, let alone extrapolated to what a lower effort tier would show. It is recorded as a secondary reference point only: at minimum, it gives no indication of *headroom* (i.e., nothing here suggests the current tier is doing more work than necessary) — if anything, wall-clock time went up, not down, across the same-effort model transition, though the confound prevents treating that as a quality-relevant signal either way.

**Reading**: this is the same "instrumentation exists in principle, but the actual sample is empty" state #1228's own commit message anticipated ("blocked #1064, #939, and #1146"). There is no way to responsibly evaluate whether `high`/`medium` would hold up for `--opus`'s specific workload without either (a) real token/quality samples at a lower tier, which do not exist, or (b) a deliberate single-Issue trial explicitly authorized by a human (not something this Issue's `/code` phase should initiate unilaterally against arbitrary backlog Issues, per the same rationale `docs/tech.md`'s `#939` Fable 5 note gives for declining to spawn unauthorized trial runs).

## Analysis 5 — `--max` flag positioning under Opus 5

`run-spec.sh --opus --max` force-overrides `EFFORT="max"` regardless of the `--opus`/`--fable` branch (`scripts/run-spec.sh`'s `--max` case sets `EFFORT="max"` unconditionally last). Opus 5's guidance (§3.2) reserves `max` for "extremely difficult, latency-insensitive tasks only" — a narrower and more specific carve-out than Opus 4.8's framing ("diminishing returns risk; reserve for intelligence-demanding experimental tasks," which read more as a general caution than a defined use case).

`--max` on the `--opus` path is an explicit, opt-in, per-invocation override — never the default — reserved for cases where a human or `/auto` operator judges a specific L-size spec to be unusually difficult and is willing to accept the added latency. This is precisely the shape of Opus 5's "extremely difficult, latency-insensitive" carve-out: an intentional, case-by-case escalation rather than a blanket setting. If anything, Opus 5's more specific guidance makes the *existing* `--max` positioning a *better* fit than it was under Opus 4.8's vaguer "experimental tasks" framing — no change to the flag's semantics or its documentation is needed; the rationale underneath it is reaffirmed, not merely carried over unexamined.
